# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo does

A weekly calculation that measures how much skill (vs. luck) each person in a friend group shows when picking sports bets. For each picker, their realized record (wins/losses/pushes) and the American odds of each pick are used to compute an implied win probability per bet (assuming no house edge). The exact distribution of possible win counts under those implied probabilities is then computed (a Poisson-binomial: the sum of independent win/lose picks, each with its own probability), and a mid-p value `P(W > w) + ½·P(W = w)` is computed against the picker's actual win count `w`. Lower p-value = more likely their record reflects skill rather than chance.

## Commands

Dependency management uses `uv`.

```shell
uv sync                 # install dependencies
uv run ruff check .     # lint
uv run pytest           # tests (tests/, fast -- exact math, no simulation)
```

After updating a season's CSVs (`data/<year>/parlay_tracker_nfl.csv` / `parlay_tracker_cfb.csv`) with a new week's picks, regenerate the site's data:

```shell
uv run python scripts/generate_data.py
```

This always **rebuilds `data.json` from scratch** — there is no incremental/upsert mode, and no `--date`/`--season` flags. Every checkpoint's date is deterministically computed from each `data/<year>/season.json` config (Week 1 date per sport, +7 days per subsequent week), not passed in or inferred from when the script happens to run. Safe to re-run any time.

`tests/` covers `simulate.py` (including the exact distribution vs. brute-force enumeration of every outcome) and `generate_data.py` (CSV validation, NFL/CFB week pairing, all-time stacking) using temp `data/` dirs. `pyproject.toml` puts `scripts/` on pytest's `pythonpath` so tests can `import generate_data`.

## Architecture

- `src/degen_sim/simulate.py` holds the core logic: `implied_probability` (American odds -> implied win probability), `PickInfo`, `build_pick_infos` (per-picker win/loss/push counts + odds from a picks dataframe), `win_distribution` (exact P(W = k) by convolving in one pick at a time, O(n²)), `p_value` (the mid-p value at the picker's win count), and `compute_standings` (a sorted p-value row per picker). This replaced an earlier 1,000,000-trial Monte Carlo simulation: same numbers to within ~0.001, but exact, deterministic (no seed), and effectively instant. The module is still named `simulate.py` for history's sake.
- `data/<year>/parlay_tracker_nfl.csv` and `data/<year>/parlay_tracker_cfb.csv` are the raw input logs for that season, one row per pick, columns: `Week, Pick (picker name), Bet, Odds (American), Win (Y/N/P)`. A blank (or whitespace-only) `Win` means not graded yet and the row is skipped; resolved rows are validated on load (`load_dated_picks`: `Win` is stripped/uppercased then must be Y/N/P, `Odds` must be <= -100 or >= +100, `Week` a whole number, `Pick` non-blank) and any bad row aborts the run with its file + line number. Updated by hand each week as game results come in. Note: **`data/` is gitignored** (`/data/*` in `.gitignore`) — the pick history itself is not committed to this repo; only the derived `data.json` is. Worth confirming with whoever maintains the CSVs that they're backed up some other way.
- `data/<year>/season.json` gives each sport's Week 1 date plus `cfb_week_offset` (how many weeks ahead CFB's numbering runs vs. NFL's, e.g. `1` means CFB week 2 = NFL week 1). A pick's calendar date is `week1_date + 7*(Week-1) days`, computed independently per sport since NFL/CFB week numbers don't share a calendar. This is the *only* source of dates in the whole pipeline — nothing is inferred from when the script happens to run.
- `scripts/generate_data.py` is the only entry point for producing results (`build_data(data_dir)` does the work; `main` just writes it out), and it always **rebuilds `data.json` from scratch** (no incremental/upsert mode, no date/season CLI flags — everything is deterministic from the CSVs + `season.json` configs, so re-running is always safe). Only 4-digit `data/<year>/` folders count as seasons (`discover_seasons`). For each one it builds three independent checkpoint timelines, each as a list of "cuts" (a cutoff date + every pick counted toward it):
  - `nfl` / `cfb`: one checkpoint per distinct date that sport has a game on (`sport_cuts`), standings cumulative through that date.
  - `combined`: **not** just the union of the other two. It pairs each NFL week with the CFB week `cfb_week_offset` ahead of it into one checkpoint (`combined_cuts`), dated by whichever of the two week's dates is later (and only counting a sport's date if it actually has picks by then — a sport that hasn't started yet shouldn't push the date forward). This is why "combined" has its own, coarser checkpoint list rather than one checkpoint per interleaved NFL+CFB date.
  Every discovered season gets an entry (even an empty `{combined: [], nfl: [], cfb: []}` one) so the website always has a tab for it. `data.json["all_time"]["weeks"]` reuses every season's own cuts (so Combined keeps its NFL/CFB week pairing) but stacks **every earlier season's full picks** underneath each one — not scoped to one season. This is why, e.g., 2026 Week 1's all-time checkpoint already includes all of 2025's picks as part of the distribution, rather than restarting from zero. `data.json` has no timestamp and no separate "latest" standings — both the season and all-time standings tables just use the last checkpoint in the list — so re-running on unchanged CSVs produces an identical file.
- `index.html` + `data.json` (both at repo root) are a static website published via GitHub Pages. Plain vanilla JS (no build step, no framework) that fetches `data.json` client-side and renders tables/canvas charts — mirrors the pattern used in the sibling `top_chef_fantasy` repo. The page has a season tab bar (each season found in `data.json.seasons`, newest first, plus "All-Time") on top of the existing sport tabs (Combined/NFL/CFB) — because each sport now has its own checkpoint timeline, the checkpoint list itself depends on *both* tabs, not just the season one (see `getCheckpointsFor(sport)`). Every checkpoint is a week, in season mode (`season.weeks[sport]`) and all-time mode (`all_time.weeks[sport]`) alike — both shapes are `{label, standings}` so the same render functions work for either. Chart x-axis labels drop the year (`axisLabel()`) unless the visible checkpoints span more than one calendar year (i.e. the All-Time view once it crosses a season boundary), in which case the year is kept so the axis doesn't look like it repeats or goes backwards. Ranking everywhere (table, rank chart, trend arrows, leader, snapshot 🔥) goes through `rankRows()`, which gives tied p-values a shared rank (shown as e.g. `T8`) — ties still happen when pickers have identical records at identical odds (e.g. several going 1-0 at -105 in Week 1). Header stats follow the selected sport tab. Picker names go through `esc()` before any `innerHTML`. Both charts are drawn by the shared `renderLineChart()`. `data.json` **is** the season's historical record — there's no other source of point-in-time snapshots, so it should only ever be produced by `scripts/generate_data.py`, never hand-edited.

## Known methodology limitations (not bugs — don't "fix" without discussion)

The website's Methodology section documents these; they're intentional simplifications, not oversights:

- **p-values are mid-p, not `P(W >= w)`, on purpose.** `p_value` returns `P(W > w) + ½·P(W = w)`. Because W is a whole number, the plain `P(W >= w)` counts an exact tie with the real record as "at least as good", which biases it upward: a no-skill picker averages `½ + ½·Σ P(W=k)²` (~0.59 at 10 picks, ~0.55 at 30), a record exactly at expectation reads as cold, and every winless picker lands at exactly 1.0 regardless of odds. Mid-p averages exactly ½ under no skill at any sample size (it's the expected value of the textbook randomized p-value), and its lower-tail counterpart is exactly `1 - mid-p`, so hot and cold read symmetrically. The trade-off: it isn't strictly conservative as a formal α-level test, which doesn't matter here since the site ranks and describes rather than running yes/no significance tests. Switching to mid-p reordered 30 of 96 checkpoints, but only between near-ties (<~0.005 apart) or pickers with very few picks, where the old bias was largest. The test `test_p_value_averages_one_half_under_no_skill` guards the property. The vig was deliberately *not* removed at the same time (see next bullet).

- **Vig is not removed.** `implied_probability` (in `simulate.py`) converts a bet's American odds straight to an implied probability, which still contains the sportsbook's built-in edge (e.g. -110 implies ~52.4%, when a truly fair coin-flip line would be 50%). This means the whole group's p-values trend systematically above 0.5 even at real, zero-edge skill — confirmed empirically: across every season checkpoint, 72% of picker rows sit above p=0.5 (as of Sep 2026; it was 87% before the mid-p switch below removed the discreteness bias). p-values should be read as relative rankings within a week, not absolute "skill" proof. Properly de-vigging would require the odds on the *other* side of each line, which isn't captured in the CSVs.
- **Pushes are intentionally included in the distribution, not excluded.** In `build_pick_infos`, `odds`/`num_games` include every pick (win, loss, *and* push), while `num_wins` (the value compared against) only counts wins. This looks like a bug at first glance — pushes appear to add an extra coin flip with no real-world counterpart — but it isn't: `num_wins`/`num_games` implicitly model a binary **Win vs. Not-Win** event per pick (Not-Win = loss or push), and a real push *is* a real "Not-Win" observation, correctly counted as 0 toward `num_wins`. Dropping push picks from the distribution instead (as an "obvious fix") would actually be worse — it discards a real, informative outcome. The one legitimate residual nuance: `implied_probability` technically estimates P(Win | bet decided), not unconditional P(Win), so it's a mild over-estimate specifically for push-eligible bets (e.g. spreads/totals on common margins like 3 or 7) — a narrow, minor effect, unlike the vig issue above which touches every single pick.
